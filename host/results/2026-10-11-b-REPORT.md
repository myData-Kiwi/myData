**Outcome correct** (added after the round, computed from the same logs) applies the same strict test to the calls that stood: a call the code rejected is ignored if the model later made an accepted call to the same tool. A run whose last call was rejected, or that never corrected a rejection, still fails. Strict scoring is unchanged from the first round: right tools, every argument strictly right, nothing invented, and the run ends the right way. A call the code rejects counts as an extra call, even when the model then fixes it.

**Hand-review rule.** Hand review only covers what the scorer judges by pattern-matching free text: the answer to a no-suitable-tool request and the answer to a no-tool question. Tool choice, arguments and how the run ended are never hand-reviewed. A refusal passes if a person reading it would say it tells the user the assistant cannot do the action, and it neither claims the action was done nor offers to do that action itself; suggesting something the tools can do instead, or telling the user how to do it themselves, is fine. A no-tool answer passes if it gives the right answer.

The refusal part of this rule is automated in `scoring.py`, so the raw score already applies it. An offer fails a refusal only if it is in the first person and names the requested action within four words; the action is a general action verb or one of the request's own imperative verbs. On the 2026-10-11 run this automation reproduces all 5 hand overrides and none of the 3 hand-confirmed failures (`tests/test_hand_review_rule.py`).

## Why chains still fail

Each of the 11 failing chain requests falls into one of three groups. All of them failed on every rep.

1. **The lookup is skipped (BC02, BC03, BC07, BC09, BC10).**
   - The model goes straight to the final action without fetching the fact it needs.
   - It then either invents the fact (BC07 date "next friday", BC10 address) or writes around it. BC02 asks Hannah for the new time instead of giving it; BC09 says "please find the booking reference attached".
2. **A description is passed as an argument instead of being looked up (BC04, BC08, BC11).**
   - Examples: `date="the day of Farah's housewarming"`, `date="that evening"`, `date="the day Vikram Menon sent the plan for his safari"`.
   - The resolver rejects them correctly. In BC11 (2 reps) the model then recovered properly: it searched mail and then photos for 8 November. Strict scoring still fails that, because of the rejected first call.
3. **Wrong source, or an incomplete lookup (BC01, BC05, BC15).**
   - BC01 searched photos for "last month" instead of finding the day in the calendar.
   - BC05 searched mail for "the person I'm meeting" instead of looking at tomorrow's calendar.
   - BC15 checked the calendar for "Ravi flat inspection", never read Ravi's email, and answered "You are free".

## What a planner would need to fix

The common failure is that the model treats a chained request as one step. A planner step would have to do the following:

1. **Name the facts before acting.** Before any action, list the facts the final action needs (date, time, address, reference, person) and, for each one, where it lives: the user's words, the calendar, mail, photos or contacts. This fixes groups 1 and 3, but only if the planner gets the source right more often than the model does now. BC05 and BC15 show the same model getting sources wrong.
2. **Turn references into lookups.** A reference such as "the day of X", "that evening" or "when Y wants to come round" becomes a lookup step whose result supplies the value. It is never passed through as an argument. This fixes group 2.
3. **Run lookups first, in code.** Execute the lookup steps, then give the model the results and ask it only to fill in the final action's arguments. The grounding check (c) then verifies that every fact in the final action came from those results.
4. **Stop when a lookup returns nothing.** Tell the user, rather than composing around the gap (BC09's "attached" reference, BC10's invented address).
5. **Shape and cost.**
   - Shape: one extra model call with a JSON schema such as `{final_action, needs: [{fact, source_tool, lookup_args}]}`.
   - Code checks the plan: every need has a source tool, and the final tool exists.
   - Cost: about one more model call per chained request, roughly +4 s at today's median.
   - Risk: the plan step makes the same source mistakes. It must be measured on a new frozen set, because set 2026-10-11-b has now been seen.

Measured with `python -m mydata.feasibility timing` (`results/2026-10-12-timing/`). Every model call's own counters come from Ollama. Cache reuse is inferred, because Ollama reports the full prompt length even when it reuses a cached prefix. **What this says**

- **Generating text is the cost.** The phrasing call, which writes the answer from the tool's result, is 77% of the time to the final answer. Most of it is generation at about 8.5 tokens a second: a median of 50 tokens takes 5.9 s, and longer answers pull the mean up to 11.5 s. The tool-choice call writes about 23 tokens (2.6 s). Tool execution (validation, grounding, the fake tool and the engine) rounds to 0.00 s.
- **Reading the prompt is cheap only because of the prefix cache.** The system prompt plus the six tool definitions are about 1,250 tokens, and every call reused them from the cache. Read cold, the same prompts took about 25 to 28 s on this machine under this load. This has consequences:
  - **The system prompt and tool definitions must stay byte-identical across requests.** Per-request tool filtering, fix (b), changes them per request. That likely explains part of the 0.6 s it added in round 2, and why it is off.
  - **A host restart, or another model evicting this one, costs about 25 s on the next request.**
- **Where time could be cut** (observations, nothing changed):
  - Let code render the tool's result for single read requests instead of a second model call. That removes the phrasing call: about 75% of the time.
  - Ask for shorter answers.
  - Keep the model warm (`keep_alive`) and the prefix stable.
- **Background load.** This was not a quiet machine (see the note under the heading of this section). The model ran entirely on the GPU, so the load mostly affects the CPU-side work. The absolute seconds are probably somewhat high; the split between the parts is the robust result.
